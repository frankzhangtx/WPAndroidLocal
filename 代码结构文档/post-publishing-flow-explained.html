Feature Analysis

WordPress Android 发帖流程分析

这份文档沿着实际源码串起“新建或编辑帖子 -> 预发布设置 -> 确认发帖 -> 落库与上传 -> 结果提示”这条主链路。 代码上，它不是一条单文件流程，而是由 ActivityLauncher、两个编辑器宿主 EditPostActivity/GutenbergKitActivity、预发布底部页 Prepublishing*、以及上传层 StorePostViewModel / UploadUtils 共同完成。

主入口：WordPress/src/main/java/org/wordpress/android/ui/ActivityLauncher.java
编辑器宿主：WordPress/src/main/java/org/wordpress/android/ui/posts/EditPostActivity.kt
块编辑器宿主：WordPress/src/main/java/org/wordpress/android/ui/posts/GutenbergKitActivity.kt
上传与反馈：WordPress/src/main/java/org/wordpress/android/ui/uploads/UploadUtils.java
我对这条链路的结论

触发发帖动作的按钮，绝大多数不会直接调用上传接口，而是先进入预发布底部页。 用户在底部页里只是在切换 Publish / Tags / Categories / Social 等状态， 真正的“提交”会回到宿主 Activity，再由它统一做邮箱校验、空内容校验、状态写回和上传。

预发布页是状态机，不是上传层 真正上传前会先更新 PostModel 无网时会落本地并排队上传
阅读顺序

先看入口，再看底部页如何导航，随后看提交时的校验与写库，最后看上传完成后的 snackbar 收尾。

入口层

ActivityLauncher.editPostOrPageForResult() 会把站点和 postLocalId 交给编辑器，避免直接传巨大的 PostModel。

动作层

performPrimaryAction() 根据主按钮类型决定是打开预发布页，还是直接保存草稿。

提交层

performPostUpdateAndPublish() 先改 PostModel 状态，再交给 StorePostViewModel 保存并上传。

反馈层

UploadUtils.handleEditPostModelResultSnackbars() 依据结果 extras 决定提示、重试或“查看/同步”。

流程总览

发帖流程的真实执行顺序

这条链路的关键不是“点了发布就立刻上传”，而是先把编辑器中的内容、站点能力和发布意图统一收口， 再由宿主 Activity 决定是否能真正进入上传阶段。

1. 入口与起点

从列表页、我的站点、阅读页、通知页等入口发起新建或编辑时，都会走到 ActivityLauncher 的编辑器启动方法。对“已有帖子”的编辑场景， 关键方法是 editPostOrPageForResult()。它只传 site 和 postLocalId，避免把整个 PostModel 直接塞进 Intent。 

// 入口只负责把站点和本地 post id 交给编辑器。
public static void editPostOrPageForResult(Activity activity, @NonNull SiteModel site, @Nullable PostModel post) {
    if (post == null) {
        ToastUtils.showToast(activity, R.string.post_not_found, ToastUtils.Duration.SHORT);
        return;
    }

    EditorLauncherParams params = EditorLauncherParams.Builder.forSite(site)
            .postLocalId(post.getId())
            .loadAutoSaveRevision(false)
            .build();

    Intent editorIntent = EditorLauncher.getInstance().createEditorIntent(activity, params);
    activity.startActivityForResult(editorIntent, RequestCodes.EDIT_POST);
}

为什么这里不直接传 PostModel

源码里已经写明原因：内容字段很大，直接传对象容易触发 TransactionTooLargeException，所以改为传 postLocalId。

新建与编辑的区别

新建帖子会走 addNewPostForResult()，编辑已有帖子会走 editPostOrPageForResult()。两者最终都落到编辑器宿主 Activity。

2. 预发布底部页

performPrimaryAction() 是宿主 Activity 的主按钮分流点。除 SAVE 外，大多数动作都会先打开 PrepublishingBottomSheetFragment，让用户在提交前确认发布方式、标签、分类和社交联动。 

// 主按钮分流：保存直接走本地保存，其余大多先打开底部页。
private fun performPrimaryAction() {
    when (primaryAction) {
        PrimaryEditorAction.PUBLISH_NOW -> {
            analyticsTrackerWrapper.track(Stat.EDITOR_POST_PUBLISH_TAPPED)
            showPrepublishingNudgeBottomSheet()
            return
        }

        PrimaryEditorAction.UPDATE,
        PrimaryEditorAction.CONTINUE,
        PrimaryEditorAction.SCHEDULE,
        PrimaryEditorAction.SUBMIT_FOR_REVIEW -> {
            showPrepublishingNudgeBottomSheet()
            return
        }

        PrimaryEditorAction.SAVE -> uploadPost(false)
    }
}

底部页本身也不是上传层，它更像一个导航壳。PrepublishingViewModel 维护当前屏幕， 处理返回键，并把最终的提交意图发回宿主 Activity。 

// Bottom sheet 负责屏幕切换和最终提交事件转发。
fun onActionClicked(actionType: ActionType, bundle: Bundle? = null) {
    when (actionType) {
        is ActionType.PrepublishingScreenNavigation -> {
            currentScreen = actionType.prepublishingScreen
            navigateToScreen(actionType.prepublishingScreen, bundle)
        }
        is ActionType.Action -> handleAction(actionType)
    }
}

fun onSubmitButtonClicked(publishPost: PublishPost) {
    onCloseClicked()
    _triggerOnSubmitButtonClickedListener.postValue(Event(publishPost))
}

当前屏幕

HOME、PUBLISH、TAGS、CATEGORIES、ADD_CATEGORY、SOCIAL 构成完整的预发布界面状态机。

返回键逻辑

在 CATEGORIES 和 ADD_CATEGORY 页面按返回键时，先触发子页面回传，再逐级回到 HOME，最后才关闭底部页。

3. 提交与发布

这里才是“发帖”真正发生的地方。提交按钮回到宿主 Activity 后，先把编辑器里的 title/content 同步回 EditPostRepository，然后检查邮箱是否验证、内容是否可发布，最后才决定是写入数据库、直接上传，还是仅本地保存。 

// 发布前先过两个硬校验：邮箱验证和内容可发布性。
private fun shouldPerformPostUpdateAndPublish() : Boolean {
    val account: AccountModel = accountStore.account
    if (!account.emailVerified) {
        storePostViewModel.hideSavingProgressDialog()
        // 弹窗要求先验证邮箱，用户确认后会退回草稿保存路径。
        return false
    }

    editPostRepository.getPost()?.let {
        if (!postUtilsWrapper.isPublishable(it)) {
            storePostViewModel.hideSavingProgressDialog()
            editPostRepository.updateStatusFromPostSnapshotWhenEditorOpened()
            ToastUtils.showToast(this, getString(R.string.error_publish_empty_post), ToastUtils.Duration.SHORT)
            return false
        }
    }
    return true
}
// 通过校验后，先写回 PostModel 的状态，再交给 StorePostViewModel。
private fun performPostUpdateAndPublish(publishPost: Boolean) {
    storePostViewModel.showSavingProgressDialog()
    val isFirstTimePublish: Boolean = isFirstTimePublish(publishPost)
    editPostRepository.updateAsync({ postModel: PostModel ->
        if (publishPost) {
            if (postModel.status == PostStatus.SCHEDULED.toString()) {
                postModel.setDateCreated(dateTimeUtils.currentTimeInIso8601())
            }
            if (uploadUtilsWrapper.userCanPublish(site)) {
                postModel.setStatus(PostStatus.PUBLISHED.toString())
            } else {
                postModel.setStatus(PostStatus.PENDING.toString())
            }
            postEditorAnalyticsSession?.setOutcome(Outcome.PUBLISH)
        } else {
            postEditorAnalyticsSession?.setOutcome(Outcome.SAVE)
        }
        postModel.setChangesConfirmedContentHashcode(postModel.contentHashcode())
        true
    }) { _: PostImmutableModel?, result: UpdatePostResult ->
        if (result === Updated) {
            val activityFinishState: ActivityFinishState = savePostOnline(isFirstTimePublish)
            storePostViewModel.finish(activityFinishState)
        }
    }
}

publishPost = true 时发生什么

如果用户有权限，会把状态设为 PUBLISHED；如果没有权限，则改成 PENDING，也就是提交审核而不是立即公开。

publishPost = false 时发生什么

这条分支更像“保存并退出”。它仍然会写入内容快照，但不会强制改成发布态。

4. 结果处理

StorePostViewModel.savePostOnline() 负责先落库，再在有网时触发上传服务。 宿主 Activity 收到 onFinish 后，会把结果编码成 extras，并交给外层列表页或宿主视图做 snackbar 收尾。 

// 保存到数据库，再根据网络状态决定是否立刻触发上传。
fun savePostOnline(
    isFirstTimePublish: Boolean,
    context: Context,
    editPostRepository: EditPostRepository,
    site: SiteModel
): ActivityFinishState {
    savePostToDbUseCase.savePostToDb(editPostRepository, site)
    return if (networkUtils.isNetworkAvailable()) {
        uploadService.uploadPost(
            context, editPostRepository.id, isFirstTimePublish,
            "StorePostViewModel#savePostOnline"
        )
        SAVED_ONLINE
    } else {
        SAVED_LOCALLY
    }
}

上传层的最终反馈在 UploadUtils.handleEditPostModelResultSnackbars()。 它会读取 EXTRA_HAS_CHANGES、EXTRA_UPLOAD_NOT_STARTED、EXTRA_HAS_FAILED_MEDIA 和帖子状态， 决定是展示“已保存/已发布”、给“发布/同步”按钮，还是提示离线排队和失败媒体重试。 

// 结果收尾：把上传结果转成对应的 snackbar 交互。
public static void handleEditPostModelResultSnackbars(...) {
    boolean hasChanges = data.getBooleanExtra(EditorConstants.EXTRA_HAS_CHANGES, false);
    if (!hasChanges) {
        return;
    }

    boolean uploadNotStarted = data.getBooleanExtra(EditorConstants.EXTRA_UPLOAD_NOT_STARTED, false);
    if (uploadNotStarted && !NetworkUtils.isNetworkAvailable(activity)) {
        // 离线时：排队上传，展示可取消的提示。
        UploadWorkerKt.enqueueUploadWorkRequestForSite(site);
        return;
    }

    boolean hasFailedMedia = data.getBooleanExtra(EditorConstants.EXTRA_HAS_FAILED_MEDIA, false);
    if (hasFailedMedia) {
        // 媒体失败时：给“编辑”按钮，回到编辑器修复。
        return;
    }
    // 根据 postStatus / uploadNotStarted 选择 publish / sync / view 文案。
}
阅读指南

看这条链路时先抓住这几个点

1. 入口不等于发帖

列表页打开编辑器只是第一步，真正的发帖动作要等到宿主 Activity 的主按钮进入预发布提交路径。

2. 底部页是状态机

PrepublishingViewModel 负责屏幕切换、返回键退栈、标签预取和提交事件，不承担上传责任。

3. 提交前有硬校验

邮箱未验证或内容不可发布时，会直接中断上传，避免把明显无效的帖子送进发布链路。

4. 保存和上传被拆开了

StorePostViewModel.savePostOnline() 先写数据库，再按网络状态决定是否立刻起 UploadService。

5. 结果由 extras 决定

宿主 Activity 把“是否有改动、是否离线、是否有失败媒体”编码到 Intent extras，后续 snackbar 分支就完全依赖这些标记。

6. Classic 和 Gutenberg 共享主流程

两个编辑器宿主的函数名和实现细节不同，但主干都是 performPrimaryAction() -> 预发布页 -> uploadPost()。
