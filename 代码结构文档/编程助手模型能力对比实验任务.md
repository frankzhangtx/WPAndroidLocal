# 本工程编程助手模型对比实验任务

本文档用于在当前 WordPress Android 工程中，对同一编程助手下不同模型的编码能力做横向对比，例如 `gpt-5.4` 与 `claude code 4.6`。

## 使用建议

- 每条任务都从同一个干净基线分支开始，独立完成，不要把 6 条任务串在同一分支上。
- 统一要求模型交付：代码实现、必要测试、验证命令、改动说明。
- 建议记录 5 个指标：完成耗时、首次通过率、总提示轮数、最终测试结果、人工补救量。
- 评分时重点看 4 个方面：理解上下文能力、改动边界控制、测试意识、回归风险控制。

## 任务总览

| ID | 难度 | 任务名称 | 主要考察点 |
| --- | --- | --- | --- |
| L1 | 低 | `QueryResult` 容错增强 | 小范围修复、空值/异常处理、单测补全 |
| L2 | 低 | `SubfilterListItemMapper` 反序列化兜底 | JSON 解析鲁棒性、恢复路径防崩溃 |
| M1 | 中 | Activity Log 增加“一键清空筛选” | ViewModel + Fragment + Layout 联动 |
| M2 | 中 | Post List 搜索旧结果隔离 | 异步状态管理、竞态条件、测试设计 |
| H1 | 高 | Activity Log 筛选状态恢复 | 生命周期、状态持久化、依赖注入适配 |
| H2 | 高 | `ConnectionStatusLiveData` 现代化改造 | Android API 兼容、架构抽象、行为回归测试 |

## 低难度任务

### L1. `QueryResult` 容错增强

- 目标：增强 `QueryResult.getValue()` 的健壮性，避免空游标或非法 JSON 造成崩溃。
- 参考文件：
  - `WordPress/src/main/java/org/wordpress/android/provider/query/QueryResult.kt`
  - `WordPress/src/test/java/org/wordpress/android/provider/query/QueryResultTest.kt`
- 具体要求：
  - 当 `Cursor` 没有数据时，返回 `null`，不要抛异常。
  - 当首列内容不是合法 JSON 时，返回 `null`，不要抛异常。
  - 保持现有泛型解析能力，不能破坏 `Type` 参数分支。
  - `createCursor()` 的现有行为不要被破坏。
- 验收标准：
  - 现有测试继续通过。
  - 至少新增“空 Cursor”和“非法 JSON”两个测试用例。
  - 改动范围尽量收敛在工具类与测试文件。
- 推荐验证命令：
  - `./gradlew :WordPress:testWordPressDebugUnitTest --tests "org.wordpress.android.provider.query.QueryResultTest"`

### L2. `SubfilterListItemMapper` 反序列化兜底

- 目标：避免 Reader 子筛选在恢复损坏状态时因为非法 JSON 直接崩溃。
- 参考文件：
  - `WordPress/src/main/java/org/wordpress/android/ui/reader/subfilter/SubfilterListItemMapper.kt`
  - `WordPress/src/test/java/org/wordpress/android/ui/reader/subfilter/SubfilterListItemMapperTest.kt`
- 具体要求：
  - `fromJson()` 遇到损坏 JSON、缺失字段、无法识别的枚举值时，统一回退到 `SiteAll`。
  - 当 JSON 可解析，但无法解析出有效 blog/feed/tag 实体时，也回退到 `SiteAll`。
  - `toJson()` 的现有输出格式保持不变。
- 验收标准：
  - 至少新增“损坏 JSON”“未知类型值”“解析后找不到目标实体”三个测试场景。
  - 不允许把恢复路径上的异常继续向上抛出。
  - 现有序列化/反序列化测试继续通过。
- 推荐验证命令：
  - `./gradlew :WordPress:testWordPressDebugUnitTest --tests "org.wordpress.android.ui.reader.subfilter.SubfilterListItemMapperTest"`

## 中难度任务

### M1. Activity Log 增加“一键清空筛选”

- 目标：在 Activity Log 的筛选栏中增加一个显式的“清空全部筛选”入口。
- 参考文件：
  - `WordPress/src/main/java/org/wordpress/android/viewmodel/activitylog/ActivityLogViewModel.kt`
  - `WordPress/src/main/java/org/wordpress/android/ui/activitylog/list/ActivityLogListFragment.kt`
  - `WordPress/src/main/res/layout/activity_log_list_activity.xml`
  - `WordPress/src/test/java/org/wordpress/android/viewmodel/activitylog/ActivityLogViewModelTest.kt`
- 具体要求：
  - 当日期筛选或活动类型筛选任意一个生效时，筛选栏出现“清空全部”入口。
  - 点击后同时清空日期筛选和活动类型筛选。
  - 只触发一次列表刷新，不允许分别清空后触发两次请求。
  - 原有两个筛选芯片的单独清除能力继续保留。
  - 需要补充必要的文案资源和测试。
- 验收标准：
  - UI 状态与 ViewModel 状态一致。
  - 清空后 `emptyUiState`、`filtersUiState`、列表刷新状态都正确更新。
  - 至少覆盖“仅日期生效”“仅类型生效”“两个同时生效”三个场景。
- 推荐验证命令：
  - `./gradlew :WordPress:testWordPressDebugUnitTest --tests "org.wordpress.android.viewmodel.activitylog.ActivityLogViewModelTest"`

### M2. Post List 搜索旧结果隔离

- 目标：解决快速连续搜索时，旧查询结果可能覆盖新查询结果的竞态问题。
- 参考文件：
  - `WordPress/src/main/java/org/wordpress/android/viewmodel/posts/PostListViewModel.kt`
  - `WordPress/src/test/java/org/wordpress/android/viewmodel/posts/PostListViewModelTest.kt`
- 具体要求：
  - 当用户依次快速输入两个不同搜索词时，只允许最新搜索词对应的数据落到 UI。
  - 如果旧查询的 `LiveData` 比新查询更晚回调，也必须被丢弃。
  - 保持“空搜索词显示搜索提示”的现有行为不变。
  - 不要破坏作者筛选和普通列表模式的现有逻辑。
- 验收标准：
  - 至少补一个“先搜 A，再搜 AB，A 的结果晚到”的测试场景。
  - 至少补一个“清空搜索后不再接受旧结果”的测试场景。
  - 实现方式需要可解释，不能靠脆弱的时间等待硬凑通过。
- 推荐验证命令：
  - `./gradlew :WordPress:testWordPressDebugUnitTest --tests "org.wordpress.android.viewmodel.posts.PostListViewModelTest"`

## 高难度任务

### H1. Activity Log 筛选状态跨旋转/重建恢复

- 目标：让 Activity Log 的筛选状态在配置变更或进程重建后能够正确恢复。
- 参考文件：
  - `WordPress/src/main/java/org/wordpress/android/viewmodel/activitylog/ActivityLogViewModel.kt`
  - `WordPress/src/main/java/org/wordpress/android/ui/activitylog/list/ActivityLogListFragment.kt`
  - `WordPress/src/test/java/org/wordpress/android/viewmodel/activitylog/ActivityLogViewModelTest.kt`
  - 可能涉及 `ViewModel` 工厂/注入相关文件
- 具体要求：
  - 恢复日期筛选、活动类型筛选，以及对应的 chip 文案状态。
  - 恢复后 `emptyUiState` 必须与筛选状态一致。
  - 避免因为恢复流程导致重复初始化或重复请求第一页数据。
  - 不允许把这类短期 UI 状态写到全局偏好中，优先考虑 `SavedStateHandle` 或 `savedInstanceState` 方案。
- 验收标准：
  - 至少覆盖“仅日期筛选恢复”“日期+类型同时恢复”“恢复后再清空”的测试场景。
  - 改动不仅能恢复数据值，还要恢复界面语义状态。
  - 对初始化流程、依赖注入和测试可维护性有清晰处理。
- 推荐验证命令：
  - `./gradlew :WordPress:testWordPressDebugUnitTest --tests "org.wordpress.android.viewmodel.activitylog.ActivityLogViewModelTest"`

### H2. `ConnectionStatusLiveData` 现代化改造

- 目标：在保留现有行为语义的前提下，把网络状态监听从旧广播模型逐步迁移到更现代的实现。
- 参考文件：
  - `WordPress/src/main/java/org/wordpress/android/viewmodel/helpers/ConnectionStatusLiveData.kt`
  - `WordPress/src/test/java/org/wordpress/android/viewmodel/helpers/ConnectionStatusLiveDataTest.kt`
- 具体要求：
  - 在较新 Android API 上优先使用 `ConnectivityManager.NetworkCallback` 一类的现代方案。
  - 对旧 API 保留兼容路径，不能直接删掉低版本支持。
  - 保持现有“只在可用性变化时发出事件”的语义，不要因为 Wi‑Fi/蜂窝切换制造重复事件。
  - `onActive()` / `onInactive()` 的注册和反注册必须安全，不能泄漏，也不能因为重复调用而崩溃。
  - 如果现有实现不易测试，可以引入最小必要的抽象层，但不要过度设计。
- 验收标准：
  - 单测至少覆盖“网络可用”“网络不可用”“重复相同状态不重复发射”“生命周期反注册”四类场景。
  - 需要明确处理新旧 API 分支，而不是只改一处判断。
  - 代码结构要便于后续继续演进，而不是把复杂逻辑硬塞回一个类里。
- 推荐验证命令：
  - `./gradlew :WordPress:testWordPressDebugUnitTest --tests "org.wordpress.android.viewmodel.helpers.ConnectionStatusLiveDataTest"`

## 建议评分维度

- 正确性：功能是否按题意完成，是否引入明显回归。
- 改动质量：是否把逻辑放在合适层级，命名与边界是否清楚。
- 测试质量：是否补了关键路径与边界条件，而不是只补“快乐路径”。
- 工程适配度：是否遵守现有项目风格，而不是另起一套写法。
- 沟通成本：完成任务过程中需要额外追问或人工修正的次数是否过多。

## 备注

- `M1` 与 `H1` 都落在 Activity Log 模块，实验时建议分别从同一个基线分支独立执行。
- 如果想进一步拉大模型差异，可以在同一题下追加一条统一约束：`必须补测试且测试命令需通过`。
