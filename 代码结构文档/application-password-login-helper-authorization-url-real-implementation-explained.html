ApplicationPasswordLoginHelper.getAuthorizationUrlComplete 真实 URL 拼接链路

这次关注的不是测试替身，而是生产代码里授权 URL 真正怎么得到。结论很明确： 它不是用 siteUrl + 固定路径 在当前类里硬拼出来的，而是分成两段， 先通过 apiDiscovery 拿到基础授权 URL，再由 appendParamsToRestAuthorizationUrl 本地补上 app_name 和 success_url。

主实现：WordPress/src/main/java/org/wordpress/android/ui/accounts/login/ApplicationPasswordLoginHelper.kt
旁证：libs/fluxc/src/main/java/org/wordpress/android/fluxc/network/rest/wpapi/site/SiteWPAPIRestClient.kt
字符串资源：WordPress/src/main/res/values/strings.xml
核心结论 最终返回的授权 URL 可以概括成： applicationPasswordsUrl(discovery.authentication) 再追加 ?app_name=<当前 App 名称+设备名>&success_url=<回调 Scheme>。 其中基础 URL 来自 discovery 结果，当前仓库的本地证据强烈表明它通常是 .../wp-admin/authorize-application.php 这一类地址，而不是前一个测试里 mock 的 /wp-json/wp/v2/application-passwords/authorization。

// ApplicationPasswordLoginHelper.kt:53-77
suspend fun getAuthorizationUrlComplete(siteUrl: String): String =
    try {
        getAuthorizationUrlCompleteInternal(siteUrl)
    } catch (throwable: Throwable) {
        handleAuthenticationDiscoveryError(siteUrl, throwable)
    }

private suspend fun getAuthorizationUrlCompleteInternal(siteUrl: String): String {
    when (val urlDiscoveryResult = wpLoginClient.apiDiscovery(siteUrl)) {
        is ApiDiscoveryResult.Success -> {
            // 第一段：从 discovery 成功结果里取“基础授权 URL”
            val authorizationUrl =
                discoverSuccessWrapper.getApplicationPasswordsAuthenticationUrl(urlDiscoveryResult)

            val apiRootUrl = discoverSuccessWrapper.getApiRootUrl(urlDiscoveryResult)
            if (apiRootUrl.isNotEmpty()) {
                // 这是缓存副作用，不参与最终 URL 字符串拼接
                apiRootUrlCache.put(UrlUtils.normalizeUrl(siteUrl), apiRootUrl)
            }

            // 第二段：在基础授权 URL 上追加 query 参数
            val authorizationUrlComplete =
                uriLoginWrapper.appendParamsToRestAuthorizationUrl(authorizationUrl)

            return authorizationUrlComplete
        }
        else -> return ""
    }
}

// ApplicationPasswordLoginHelper.kt:357-373
fun appendParamsToRestAuthorizationUrl(authorizationUrl: String?): String {
    if (authorizationUrl.isNullOrEmpty()) return authorizationUrl.orEmpty()

    val userDeviceName = DeviceUtils.getInstance().getDeviceName(context)
    val (appName, successUrl) = if (buildConfigWrapper.isJetpackApp) {
        context.getString(R.string.application_password_app_name_jetpack, userDeviceName) to
            "jetpack://app-pass-authorize"
    } else {
        context.getString(R.string.application_password_app_name_wordpress, userDeviceName) to
            "wordpress://app-pass-authorize"
    }

    return authorizationUrl.toUri().buildUpon().apply {
        appendQueryParameter("app_name", appName)
        appendQueryParameter("success_url", successUrl)
    }.build().toString()
}

这里最值得注意的是：siteUrl 只作为 discovery 的输入， 并没有在当前类里直接被拿来做字符串拼接。 也就是说，真实代码没有类似 "$siteUrl/wp-admin/authorize-application.php" 这样的写法。

阅读抓手

先抓住这 5 点，再看完整代码就不会混淆测试值和生产值。

1. 基础授权 URL 来自 discovery，不来自本地硬编码路径

wpLoginClient.apiDiscovery(siteUrl) 成功后， DiscoverSuccessWrapper 再调用外部的 applicationPasswordsUrl(...) 取出授权地址。

2. 当前仓库的强旁证指向 authorize-application.php

SiteWPAPIRestClient 直接把 APPLICATION_PASSWORDS_URL_SUFFIX 定义成 authorize-application.php，并从 authorization endpoint 反推 adminUrl。 这说明真实 endpoint 的形状是 WordPress admin 授权页。

3. 本地真正拼接的是两个 query 参数

appendParamsToRestAuthorizationUrl 只追加 app_name 和 success_url， 不负责生成基础路径。

4. WordPress 与 Jetpack 的差异只在参数值

分支由 BuildConfigWrapper.isJetpackApp 控制。 WordPress 用 WordPress Android App on %s 和 wordpress://app-pass-authorize； Jetpack 用 Jetpack Android App on %s 和 jetpack://app-pass-authorize。

5. 失败时直接返回空串

无论是 discovery 抛异常还是返回失败分支， handleAuthenticationDiscoveryError 最终都会返回 ""，调用方据此走错误或降级逻辑。
