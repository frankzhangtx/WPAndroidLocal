# AI Coding Benchmark Product Cases for WPAndroid

本文档基于当前 WordPress Android 工程设计 15 个编程任务，用于对比不同模型、是否提供工程知识库、不同 harness/自动化工程环境下的编程能力差异。

这些 case 按产品需求方式描述，不直接告诉实现者应该修改哪个文件、哪个函数或哪个类。实现者需要自行理解工程结构、定位相关代码、设计实现方案并补齐验证。

统一投放要求：

- 每个 case 作为独立任务投放。
- 不向实现者额外提供目标文件、函数名或预设修复路径。
- 提交应包含必要的产品行为实现、回归保护和自动化测试。
- 用户可见文案必须支持本地化。
- 不允许为了通过测试而写死数据、绕过现有业务层、跳过持久化或禁用异常路径。
- 验收时以产品行为、数据一致性、测试覆盖和代码审查结果为准。

## 难度划分

- 低难度：单个产品细节或局部体验修正，通常影响一个明确交互点或展示规则。
- 中等难度：单个产品模块内的完整流程改进，通常涉及状态、加载、失败恢复或用户偏好。
- 高难度：跨多个产品入口或底层能力的系统性改造，通常涉及持久化、后台任务、通知、离线能力或跨模块一致性。

## Low-01: 统计数字在卡片上更易读

难度：低

用户场景：

用户打开站点统计页时，卡片上会展示浏览量、访客数、订阅数等数字。当前大数字展示不够自然，部分边界值会出现多余的小数，负向变化值也不够统一，影响快速扫读。

产品目标：

让统计卡片中的数字在小屏幕上更紧凑、更稳定、更容易理解，同时不改变真实数值含义。

验收标准：

- 小于 1000 的整数直接展示完整数字，例如 `999` 显示为 `999`。
- 1000 及以上使用 `K`，1000000 及以上使用 `M`。
- 整数缩写不显示多余 `.0`，例如 `1000` 显示为 `1K`，`1000000` 显示为 `1M`。
- 非整数缩写最多保留一位小数，例如 `1500` 显示为 `1.5K`，`2500000` 显示为 `2.5M`。
- 负数按同样规则展示并保留负号，例如 `-1500` 显示为 `-1.5K`。
- 0 和邮箱统计中的空值展示不发生回归。
- 不同系统语言环境下，缩写结果对自动化测试保持稳定。

非目标：

- 不要求新增 B/T 等更大单位。
- 不要求调整统计 API、图表或详情页数据源。

建议验证：

- 覆盖 0、999、1000、1500、999999、1000000、2500000、负数和邮箱统计。
- 验证英文和非英文 locale 下测试不会因小数分隔符失败。

主要能力点：产品展示规则、边界值处理、轻量回归测试。

## Low-02: 上传文件时能识别常见扩展名写法

难度：低

用户场景：

用户从系统文件选择器、云盘或第三方应用导入媒体和文档时，文件扩展名可能是大写、带点号或带空格。产品不应因为这些常见格式差异误判文件类型。

产品目标：

提升文件类型识别的容错能力，让用户能顺利上传 WordPress 支持的文件。

验收标准：

- `JPG`、`jpg`、`.jpg`、` jpg ` 都能识别为同一种图片类型。
- PDF、DOCX、MP4 等当前已支持类型也应具备相同的大小写和点号容错。
- 空输入、只有空格、只有点号、未知扩展名应安全返回“不支持/未知”，不能崩溃。
- 不改变不同站点计划下已有的类型限制规则。
- 文件类型识别来源应保持统一，避免不同上传入口对同一文件给出不同结论。

非目标：

- 不要求新增 WordPress 当前不支持的新文件类型。
- 不要求改变服务端上传限制。

建议验证：

- 覆盖图片、视频、文档、未知扩展、大小写、前导点、空白输入。
- 验证媒体选择和上传前校验使用一致的识别结果。

主要能力点：输入规范化、兼容性、安全失败。

## Low-03: 个性化列表遇到失效项时不崩溃

难度：低

用户场景：

用户在站点个性化、快捷入口或设置列表中调整项目时，本地偏好里可能残留旧版本项目。产品应忽略无效项，而不是在删除或刷新列表时崩溃。

产品目标：

提升列表类个性化功能对旧数据和边界输入的容错能力。

验收标准：

- 删除列表中的有效项目时，结果正确且原始数据不被意外修改。
- 当系统尝试删除一个不存在的位置时，列表保持不变，不崩溃。
- 空列表、负位置、超出长度的位置都能安全处理。
- 旧版本偏好中残留的无效项目不会阻止页面打开或保存。
- 相关行为对 Java/Kotlin 两类旧调用方保持兼容。

非目标：

- 不要求重做个性化页面交互。
- 不要求迁移所有历史偏好数据。

建议验证：

- 覆盖空列表、首项、末项、中间项、负位置、越界位置。
- 验证个性化页面在存在旧偏好数据时可以正常打开。

主要能力点：边界容错、旧数据兼容、低风险修复。

## Low-04: 转发文章时用户输入不能破坏编辑内容

难度：低

用户场景：

用户在 Reader 中转发文章时，应用会把引用文字、来源链接和特色图组合成一段编辑器内容。如果原文标题或引用中包含 HTML 特殊字符，生成的内容可能显示异常，甚至破坏编辑器结构。

产品目标：

让转发内容既保持 WordPress block/classic editor 结构，又能安全处理用户可控文本。

验收标准：

- 引用文字、来源标题和默认链接文字中的 `<`、`>`、`&`、引号等字符不会被当作 HTML 执行。
- WordPress block 标记、引用块、链接、图片等产品需要生成的结构保持可编辑。
- 无效来源链接不会生成可点击链接。
- 有效来源链接仍能正常生成，显示文本安全。
- Gutenberg 和 classic editor 两种输出都不回归。

非目标：

- 不要求改变转发内容的视觉设计。
- 不要求服务端清洗或 Reader API 改造。

建议验证：

- 使用包含脚本片段、特殊字符、有效链接、无效链接、带图和不带图的文章样本验证。
- 覆盖 Gutenberg 与 classic editor 两种编辑器模式。

主要能力点：内容安全、HTML 生成边界、编辑器兼容。

## Low-05: Reader 文章卡片标签更干净

难度：低

用户场景：

Reader 推荐流中的文章卡片会展示标签。部分文章标签可能为空、重复或数量过多，导致卡片拥挤、点击区域混乱。

产品目标：

让 Reader 卡片上的标签展示简洁稳定，保留有价值标签，避免布局噪音。

验收标准：

- 空标题或空标识的标签不展示。
- 重复标签只展示一次，大小写差异不应造成重复。
- 保留原始顺序中的第一次出现。
- 每篇文章最多展示 5 个标签。
- 标签点击行为和卡片宽度适配不回归。

非目标：

- 不要求改变 Reader 标签详情页。
- 不要求引入新的标签排序算法。

建议验证：

- 使用包含空标签、重复标签、大小写差异和超过 5 个标签的文章样本。
- 验证标签点击仍能进入对应标签流。

主要能力点：UI 数据清洗、顺序稳定性、小屏幕体验。

## Medium-01: 媒体选择器加载过程更可靠

难度：中

用户场景：

用户在编辑文章时打开媒体选择器，可能会筛选文件、下拉刷新、加载更多或在失败后重试。当前这些动作组合使用时，列表可能出现重复、丢失、错误状态不消失或重复加载。

产品目标：

让媒体选择器在筛选、分页、刷新和重试时表现一致，用户始终能理解当前列表状态。

验收标准：

- 首次打开时显示当前媒体来源的第一页内容。
- 筛选后列表只展示筛选结果，并明确进入“筛选结果”状态。
- 清除筛选后恢复普通列表状态。
- 加载下一页时，已有内容保留，新内容追加；不能因为翻页丢失第一页。
- 当没有更多内容时，不再发起无意义加载。
- 加载失败时保留已有内容并显示错误状态。
- 用户点击重试后，重试上一次有效操作；成功后错误状态消失。
- 快速连续触发加载更多不会产生重复请求或重复列表项。

非目标：

- 不要求改变媒体网格视觉设计。
- 不要求新增新的媒体来源。

建议验证：

- 用假媒体源覆盖首次加载、筛选、清除筛选、分页、失败、重试和快速连续触发。
- 验证列表状态变化顺序稳定，不依赖真实时间等待。

主要能力点：状态流、分页、失败恢复、异步测试。

## Medium-02: 统计卡片个性化不会重复或乱序

难度：中

用户场景：

用户可以在新统计页自定义卡片显示和顺序。如果反复添加、删除或移动同一张卡片，产品不应出现重复卡片、顺序错乱或无意义刷新。

产品目标：

让统计卡片个性化设置具备幂等性，旧配置或异常配置也能被安全修复。

验收标准：

- 添加已存在的卡片不会产生重复项。
- 删除不存在的卡片不会改变配置。
- 将第一张卡片上移、最后一张卡片下移或移动不存在的卡片不会触发无意义变化。
- 读取旧配置时，如果发现重复卡片，应保留第一次出现的顺序并清理重复项。
- 读取无法解析或包含非法卡片类型的配置时，安全恢复到默认配置。
- 只有配置真正变化时，页面才收到配置变更通知。
- 不同站点的配置互不影响。

非目标：

- 不要求重新设计统计卡片管理界面。
- 不要求新增统计卡片类型。

建议验证：

- 覆盖重复添加、无效删除、边界移动、旧配置重复项、坏配置、多个站点。
- 验证页面观察到的配置变更次数符合预期。

主要能力点：用户偏好持久化、幂等操作、旧数据修复。

## Medium-03: Reader 已读/未读切换反馈更及时

难度：中

用户场景：

用户在 Reader 中将文章标为已读或未读时，希望界面立即反馈。如果网络请求失败，应用应恢复原状态并说明失败原因，而不是让本地状态和服务端状态长期不一致。

产品目标：

实现可靠的乐观更新：先给用户即时反馈，再根据服务端结果确认或回滚。

验收标准：

- 网络可用且用户已登录时，点击已读/未读后本地状态立即变化。
- 博客未读计数同步即时变化。
- 服务端成功后保持新状态，并记录正确的用户行为埋点。
- 服务端失败后恢复文章状态和未读计数，并展示失败消息。
- 无网络、未登录或文章不支持已读状态时，不进行乐观更新。
- 自动标记已读的静默路径不产生用户点击埋点。
- 快速连续点击同一篇文章时，不会导致未读计数多增或多减。

非目标：

- 不要求重新设计 Reader 卡片。
- 不要求改变服务端 API 协议。

建议验证：

- 覆盖成功、失败回滚、无网络、未登录、不支持状态、静默自动标记、快速重复操作。
- 验证文章状态和博客未读计数始终一致。

主要能力点：乐观更新、回滚、计数一致性、事件埋点。

## Medium-04: My Site 个性化支持一键恢复默认

难度：中

用户场景：

用户在 My Site 页面调整了快捷入口和仪表盘卡片后，可能希望快速回到默认布局，而不是逐个开关恢复。

产品目标：

为 My Site 个性化提供一键恢复默认能力，并确保只影响当前站点。

验收标准：

- 用户可以在个性化页面触发“恢复默认”。
- 仪表盘卡片恢复默认可见状态：统计、草稿文章、计划发布文章默认显示。
- 页面、活动日志、推广、写作提示等条件型卡片仍遵守站点能力和功能开关，不应强行显示。
- 快捷入口恢复默认：文章、页面、统计默认显示。
- 恢复只影响当前站点，不影响用户其他站点的个性化配置。
- 操作后页面立即刷新，不需要退出重进。
- 恢复操作有可分析的埋点。
- 当前站点不可用或页面生命周期结束时，不应崩溃。

非目标：

- 不要求新增拖拽排序。
- 不要求同步默认布局到云端。

建议验证：

- 覆盖普通站点、自托管站点、缺少页面权限的站点、多个站点切换。
- 验证恢复前后页面状态、偏好数据和埋点。

主要能力点：单模块多状态协作、站点级偏好隔离、UI 即时刷新。

## Medium-05: 批量评论操作避免离线误操作和重复提交

难度：中

用户场景：

用户在评论列表中批量批准、取消批准、移入垃圾箱或标记垃圾评论。如果设备离线或用户快速多次点击操作按钮，当前体验可能让用户误以为操作成功，或重复发送请求。

产品目标：

让批量评论操作在离线、失败和快速点击场景下可理解、可恢复、不重复。

验收标准：

- 设备离线时，批量操作不发起请求，并向用户显示无法操作的原因。
- 批量操作进行中时，相关按钮进入不可重复提交状态。
- 用户快速重复点击同一个批量动作，只能产生一次实际请求。
- 全部成功后，清空已选评论并恢复普通列表状态。
- 失败后，保留仍需用户处理的选中项，并显示错误提示。
- 失败或重试不会重复记录同一次用户操作埋点。
- 单条评论操作和撤销行为不回归。

非目标：

- 不要求实现离线队列；离线时只需阻止操作并提示。
- 不要求改变评论列表视觉布局。

建议验证：

- 覆盖离线、进行中重复点击、成功、失败、部分失败、埋点次数和单条撤销回归。

主要能力点：复杂 ViewModel 状态、重复提交保护、失败恢复。

## High-01: 不同站点计划下媒体上传限制一致

难度：高

用户场景：

用户在 WordPress.com 免费站点、付费站点和自托管站点上传媒体或文档时，可上传类型不同。当前不同入口可能给出不一致结果：有的入口允许选择，有的入口到上传时才失败。

产品目标：

建立统一的站点感知媒体策略，让选择、插入和上传前校验都遵循相同规则，并给用户明确原因。

验收标准：

- WordPress.com 免费站点不允许上传音频和仅付费/自托管支持的文档类型。
- WordPress.com 付费站点和自托管站点遵循当前产品支持的完整类型列表。
- 未知站点计划保持兼容策略，但不能错误放行明显无法识别的危险类型。
- 媒体选择阶段能过滤或标记不可上传文件，不能只等上传失败后才提示。
- 编辑器插入、普通媒体上传、自动上传路径使用同一套判断。
- 不可上传时，提示文案说明文件类型和站点限制原因。
- 图片、视频、GIF、库存媒体等原有成功路径不回归。
- 文件类型规则只有一个事实来源，避免不同入口维护不同列表。

非目标：

- 不要求改变服务端允许类型。
- 不要求新增付费升级购买流程。

建议验证：

- 覆盖免费、付费、自托管、未知计划与图片、视频、音频、文档、未知类型的组合。
- 验证媒体选择器、编辑器插入、手动上传、自动上传四类入口行为一致。

主要能力点：跨入口业务策略、共享规则抽象、用户反馈一致性。

## High-02: 评论审核支持离线排队

难度：高

用户场景：

站长在通勤或网络不稳定时处理评论，希望即使离线也能先完成审核动作，应用在网络恢复后自动提交。用户需要看到哪些评论仍在等待同步。

产品目标：

为评论审核建立可靠的离线队列，支持单条和批量操作、撤销、重试和最终同步。

验收标准：

- 离线时，单条和批量批准、取消批准、移入垃圾箱、标记垃圾评论、删除可以进入待同步队列。
- 评论列表中待同步评论有明确 pending 状态。
- 同一条评论不能同时存在相互冲突的多个待同步动作。
- 用户撤销操作时，待同步动作能被取消或以清晰规则反向处理。
- 网络恢复后，后台自动重放队列并更新本地评论状态。
- 临时网络或服务错误按退避策略重试。
- 权限、认证或评论不存在等永久失败应停止重试并提示用户。
- 应用重启后待同步队列不丢失。
- 线上即时审核、离线排队、队列重放成功和失败都有可区分的埋点。

非目标：

- 不要求支持离线编辑评论正文。
- 不要求解决多个设备同时审核同一评论的所有冲突，但必须安全失败。

建议验证：

- 覆盖入队、去重、冲突、撤销、应用重启、网络恢复、临时失败重试、永久失败停止。
- 验证列表 pending 状态和后台任务执行结果一致。

主要能力点：离线优先、持久化队列、后台重放、冲突处理。

## High-03: Reader 记录阅读进度并自动标记已读

难度：高

用户场景：

用户在 Reader 中阅读长文章时，退出后希望下次回到接近上次的位置。读完大部分内容后，应用也应帮用户自动标记已读，减少手动操作。

产品目标：

为 Reader 文章详情加入阅读进度恢复和自动已读能力，同时尊重用户手动未读选择。

验收标准：

- 每篇文章单独记录阅读进度。
- 用户重新打开文章详情时，能恢复到合理的上次阅读位置。
- 当用户阅读超过 70% 且文章支持已读状态时，自动标记为已读。
- 自动已读复用现有已读/未读业务逻辑，不能绕过一致性处理。
- 用户手动标记为未读后，本次会话内不会再次被自动标记为已读。
- 离线或未登录时只保存阅读进度，不误发远端请求。
- 自动标记成功、跳过原因、恢复阅读位置都有可分析事件。
- Reader 列表、详情页、相关文章和评论关注等现有路径不回归。

非目标：

- 不要求跨设备同步阅读进度。
- 不要求为 WebView 或编辑器实现通用阅读进度组件。

建议验证：

- 覆盖进度保存与恢复、69% 不触发、70% 触发、手动未读优先、离线、未登录、API 失败。
- 验证自动已读不会造成未读计数错误。

主要能力点：UI 事件持久化、业务规则优先级、跨 use case 复用。

## High-04: 新统计页卡片默认配置支持远端下发

难度：高

用户场景：

产品团队希望逐步调整新统计页的默认卡片顺序和可见性，不必每次都发布新版本。但已经自定义过统计页的用户不应被远端默认值覆盖。

产品目标：

支持版本化远端默认配置，并安全迁移本地配置，保护用户个性化选择。

验收标准：

- 远端配置可以定义默认可见卡片、可添加卡片、配置版本和适用条件。
- 某站点首次进入新统计页时，优先使用合法远端默认配置。
- 远端配置缺失或非法时，安全回退到本地默认配置。
- 已有本地个性化配置的站点默认不被远端覆盖。
- 当远端声明强制迁移且版本高于本地记录时，执行迁移。
- 迁移时保留用户已隐藏和已排序的有效卡片。
- 新增远端卡片按远端顺序插入合理位置。
- 未知卡片、重复卡片、空配置、当前 flavor 不支持的卡片都能安全处理。
- 远端配置刷新只影响对应站点，不导致其他站点页面闪烁或重置。
- 采用、忽略、回退、迁移远端配置的原因可诊断。

非目标：

- 不要求新增远端配置后台。
- 不要求把用户本地排序同步到服务端。

建议验证：

- 覆盖首次使用、本地配置优先、强制迁移、非法远端、未知卡片、重复项、跨站点隔离。
- 验证页面观察到的卡片顺序和可见性符合预期。

主要能力点：远端配置、版本迁移、用户偏好保护、跨站点状态隔离。

## High-05: 系统通知去重并统一点击路由

难度：高

用户场景：

用户可能同时收到 push 通知、本地提醒和后台刷新产生的通知。同一条评论、文章或草稿提醒不应在系统通知栏重复出现；用户点击或清除后，应用状态也应一致。

产品目标：

建立统一通知身份和路由策略，避免重复通知，保证点击、清除、已读状态一致。

验收标准：

- 每条通知有稳定身份，能区分来源、站点、远端对象和动作类型。
- Push、本地提醒、后台刷新产生的通知都通过统一身份判断重复。
- 同一身份的重复通知应更新已有通知或被忽略，不能生成多个重复通知。
- 不同来源但代表不同用户事件的通知不能被误合并。
- 用户清除通知后，短时间内同一事件不会被后台刷新重新弹出。
- 用户点击通知后，应用打开正确页面，并同步已读/清除状态。
- 本地草稿提醒等纯本地通知不被远端通知错误去重。
- 路由失败时有 fallback 或可诊断日志。
- 展示、去重、更新、清除、打开、路由失败都有可区分的埋点。
- Android 通知权限和通知 channel 现有行为不回归。

非目标：

- 不要求重新设计通知详情页。
- 不要求改变服务端 push payload 协议，除非现有字段无法满足稳定身份。

建议验证：

- 覆盖 push 与本地重复、刷新后重复、不同通知误合并、清除后刷新、点击路由、草稿提醒。
- 验证应用重启后去重和已处理状态仍然有效。

主要能力点：跨来源事件建模、系统通知副作用控制、路由一致性、持久化状态。
